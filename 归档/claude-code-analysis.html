背景
Claude Code 是 Anthropic 的终端 AI 编程助手。你输入提示词，它读取你的代码库、运行命令、编辑文件。 工程质量在部分地方确实令人叹服——查询循环架构、工具并发系统、权限分类器都有真正的设计思考。 但这也是一个会在你机器上执行任意命令的产品。有些选择值得公开审视。

以下每条指控均附有真实文件和行号。没有臆测，只有代码。

import 区块单独就有 244 行，从 235 个不同模块引入。

// 死代码消除：条件 import
const useVoiceIntegration = feature('VOICE_MODE')
  ? require('../hooks/useVoiceIntegration.js').useVoiceIntegration
  : () => ({ ... });

const useFrustrationDetection = "external" === 'ant'
  ? require('../components/FeedbackSurvey/useFrustrationDetection.js')
  : () => ({ state: 'closed', handleTranscriptSelect: () => {} });

// ... 还有 200 多行 import

注意 "external" === 'ant' 这类比较。它们在构建时求值，用于从公开构建中剥离 Anthropic 内部专属功能——同一个文件在服务两个完全不同的产品。

问题所在

一个有 227 个 Hook 调用、由单一组件主导的文件，实际上是无法单独测试的。每个 useEffect 都与每个 useState 相互作用，依赖数组变得无法推理。第 4114 行的 // TODO: fix this 加上 eslint-disable-next-line react-hooks/exhaustive-deps，是团队自己在承认他们知道这个问题。

应该做的：用状态机（如 XState 或简单的 reducer）驱动 15-20 个聚焦组件。REPL 有清晰的状态：初始化、等待输入、流式响应、执行工具、等待权限……68 个 useState 可以合并为一个带类型转换的状态对象。这是复杂 UI 的标准 React 架构。

02 问题
功能蔓延

89 个功能标志，960 处引用，散落各处

Claude Code 使用 Bun 的编译期 feature() 函数进行功能门控。全库中有 89个功能标志，被引用 960次。

以下是全部功能标志：

ABLATION_BASELINE AGENT_MEMORY_SNAPSHOT AGENT_TRIGGERS KAIROS KAIROS_BRIEF KAIROS_CHANNELS KAIROS_DREAM KAIROS_GITHUB_WEBHOOKS KAIROS_PUSH_NOTIFICATION VOICE_MODE BASH_CLASSIFIER BRIDGE_MODE COORDINATOR_MODE EXPERIMENTAL_SKILL_SEARCH NEW_INIT ULTRAPLAN ULTRATHINK WEB_BROWSER_TOOL DAEMON BUDDY OVERFLOW_TEST_TOOL MCP_RICH_OUTPUT SSH_REMOTE PROACTIVE VERIFICATION_AGENT TOKEN_BUDGET HOOK_PROMPTS HISTORY_PICKER QUICK_SEARCH TERMINAL_PANEL … 还有 58 个

■ 红色标注 = 可疑的实验性或早该清理的标志

除此之外，还有 472个 不同环境变量，在 1,425处 被引用。

问题所在

89 个标志意味着团队不清楚产品的形态。功能标志适合灰度发布，但当你有 KAIROS、KAIROS_BRIEF、KAIROS_CHANNELS、KAIROS_DREAM……六个独立标志时，你不是在做灰度——你是在同一个代码库里用条件 require 搭建一个完整的平行产品。那不是功能标志系统，那是没有 monorepo 工具的 monorepo。

03 问题
模块设计

61 个文件里有循环依赖的变通方案

在代码库里搜索 "break import cycle"、"avoid circular dependency"，会在 61个文件 中找到命中。开发者没有隐瞒——他们在注释里写出来了：

// types/permissions.ts
// 提取纯权限类型定义以打破 import 循环。

// schemas/hooks.ts
// 提取 Hook Zod schema 以打破 import 循环。
// settings/types.ts 和 plugins/schemas.ts 之间的循环依赖。

// tasks.ts
// 注意：内联返回数组以避免顶层 const 的循环依赖问题

// utils/bash/ast.ts (第 2218 行)
// 与 bashPermissions.ts 的循环 import。

模式总是一样的：把类型提取到单独文件、用懒 require、或内联本应 import 的代码。types/permissions.ts 和 schemas/hooks.ts 这两个文件，存在的唯一目的就是打破循环依赖。

根本原因

Tool.ts 这个中心类型试图做太多事——它从权限类型、消息类型、分析、MCP 类型、Agent 类型、进度类型、Hooks 等各处导入。这个 792 行的类型定义文件处于依赖图的中心，当核心类型导入所有东西，所有东西就导入它，循环就出现了。61 个文件不是"偶发的循环"，而是模块图从未被设计过——它有机生长，现在深度纠缠。

04 问题
类型系统滥用

出现 1,193 次的类型名

每一个分析调用都需要一次类型转换：

logEvent('tengu_startup_telemetry', {
  entrypoint: entrypoint as AnalyticsMetadata_I_VERIFIED_THIS_IS_NOT_CODE_OR_FILEPATHS,
  action: 'hint_converted' as AnalyticsMetadata_I_VERIFIED_THIS_IS_NOT_CODE_OR_FILEPATHS,
  variant: idleHintShownRef.current as AnalyticsMetadata_I_VERIFIED_THIS_IS_NOT_CODE_OR_FILEPATHS,
})

AnalyticsMetadata_I_VERIFIED_THIS_IS_NOT_CODE_OR_FILEPATHS 在整个代码库中出现 1,193次，其中 1,000 多次是显式的 as 类型转换。

出发点是好的：Claude Code 运行在真实代码库上，你不想把文件路径、源代码或密钥意外记录到分析管道中。所以他们做了一个类型，强制开发者手动确认"是的，这个字符串可以安全记录"。

但是当你要把这个 53 个字符的类型转换写 1,000 多次，它就不再是护栏了，而是变成了仪式。一周后你就不再读它了。

更好的做法

用构建器模式或带验证的辅助函数：logSafeEvent('name', { key: SafeMetadata.from(value) })——如果 value 看起来像路径或代码就抛出异常。运行时验证能捕获类型转换声称要防止的问题。长类型名什么都捕获不到，只是在"礼貌地请求"。

05 问题
奇妙的权宜之计

用 String.fromCharCode 拼写 "duck"

在 buddy/types.ts（是的，Claude Code 有一个隐藏的宠物系统）中，物种列表是这样定义的：

// buddy/types.ts
// 某个物种名与 excluded-strings.txt 中的模型代号金丝雀冲突。
// CI 检查 grep 的是构建输出而非源码，
// 所以在运行时构造值可以让字面量不出现在 bundle 中，
// 同时保持对真实代号的检查有效。
// 所有物种名统一编码。

const c = String.fromCharCode

export const duck    = c(0x64,0x75,0x63,0x6b) as 'duck'
export const goose   = c(0x67,0x6f,0x6f,0x73,0x65) as 'goose'
export const blob    = c(0x62,0x6c,0x6f,0x62) as 'blob'
export const cat     = c(0x63,0x61,0x74) as 'cat'
export const dragon  = c(0x64,0x72,0x61,0x67,0x6f,0x6e) as 'dragon'
export const octopus = c(0x6f,0x63,0x74,0x6f,0x70,0x75,0x73) as 'octopus'
export const owl     = c(0x6f,0x77,0x6c) as 'owl'
export const penguin = c(0x70,0x65,0x6e,0x67,0x75,0x69,0x6e) as 'penguin'
// ... 还有 10 种，全部十六进制编码

原因在注释里：某个物种名（可能是 axolotl 或 capybara）与 Anthropic 的内部模型代号冲突。CI 会 grep 构建输出查找这些代号作为安全金丝雀。与其给 CI 检查加一条例外规则，他们把全部 18 个物种名都十六进制编码了。

两面性

CI 检查本身可能是正确且重要的。正确的修复是给 buddy 模块加一条正则例外，而不是把每个物种名都编码成十六进制。以后读这个文件的开发者会一头雾水，不明白为什么"duck"不能直接写"duck"。

另一方面——Anthropic 工程师花时间在一个终端编程工具里做了一个有稀有度分级（从普通到传奇）、命名物种、帽子、眼睛样式和属性分布的程序化生成宠物系统——这说实话还挺迷人的。

06 问题
入口点设计

main.tsx：4,683 行的入口点

main.tsx 是 CLI 入口，共 4,683行，塞进了：

全部 CLI 命令定义
claude, init, config, mcp, doctor…
参数解析
Commander.js 完整配置
OAuth 登录流
完整实现
会话恢复 + 远程会话 + 插件加载 + MDM 配置
全在这一个文件
// 这些副作用必须在所有其他 import 之前运行：
// 1. profileCheckpoint 在繁重模块求值开始前标记入口
// 2. startMdmRawRead 与剩余 ~135ms 的 import 并行启动 MDM 子进程
// 3. startKeychainPrefetch 并行启动两个 macOS keychain 读取
//    （macOS 每次启动约 65ms）
权衡分析

架构选择是刻意的：把所有东西放在一个文件里，以最小化 import 图深度。Bun 是 eager 求值 import 的，更深的 import 树意味着更多启动延迟。他们用不可读性换来了约 135ms 的启动速度。

但懒加载命令注册表可以实现同样的效果——只在用户运行 claude init 时才加载 init 命令模块，只在需要认证时才加载 OAuth。这是其他所有 CLI 工具的做法（oclif、yargs command modules、commander 子命令拆分）。

07 问题
类型系统漏洞

条件 require() 模式：类型系统的盲区

在 REPL.tsx 和 query.ts 中大量存在这样的代码：

const reactiveCompact = feature('REACTIVE_COMPACT')
  ? (require('./services/compact/reactiveCompact.js')
     as typeof import('./services/compact/reactiveCompact.js'))
  : null

const contextCollapse = feature('CONTEXT_COLLAPSE')
  ? (require('./services/contextCollapse/index.js')
     as typeof import('./services/contextCollapse/index.js'))
  : null

REPL.tsx 有 17处 这样的模式，query.ts 有 6处。原因在于：

  • →import 会被提升并在模块加载时求值
  • →feature() 检查需要完全阻止 import 以实现死代码消除
  • →require() 是模块体内唯一的条件 import 方式
  • →但 require() 丢失类型信息，所以需要 as typeof import(...)
问题所在

每一处都是类型系统的漏洞。as typeof import(...) 在告诉 TypeScript "相信我，这是正确的类型"。如果有人改变了 reactiveCompact.js 的导出形状，这个转型会悄悄说谎——没有编译器报错，你只能在运行时发现。

动态 import() 返回 Promise 并且保留类型，是现代 JS 中条件模块加载的标准解法。Bun 支持它。

深层根因：架构跟不上增长速度

如果拉远视角，大多数问题来自同一个根本原因：Claude Code 的成长速度超过了其架构的承载能力。

你能看到历史的层叠：一个简单的终端 REPL 成长为了带有语音模式、宠物伴侣、Vim 绑定和远程会话的多 Agent 协调器。功能在标志后面的添加速度，快于旧标志的清理速度。模块图的连接增速，快于任何人划定边界的速度。

这对 Anthropic 来说并不特殊。每家快速迭代的公司都有这样的代码库。Claude Code 的案例之所以值得关注，是因为规模：这是世界上最重要的 AI 产品之一，其源码揭示了每家初创公司都存在的同样混乱的工程权衡。

代码在 ship。它能工作。大量开发者每天依赖它。这比漂亮的架构更重要。但对成本保持诚实，也是值得的。
